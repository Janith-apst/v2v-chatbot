# Phase 1 — Realtime Voice-to-Voice POC: Technical Specification

## 1. Goal

Build a frontend-only React + Vite PWA that lets a user have a realtime, full-duplex spoken conversation with Gemini via the Live API. Targeted at blind users, so the experience must be usable without sight.

The single question this phase answers: **can we get a smooth realtime voice loop in the browser using Gemini, with reliable barge-in?**

### In scope
- React 19 + Vite + TypeScript PWA
- Gemini Live API via the official `@google/genai` SDK
- Microphone capture via `AudioWorklet`, downsampled to 16 kHz PCM16
- Streaming audio playback at 24 kHz PCM16 with a queue
- User barge-in (mic stays open during model playback; on user speech the queued model audio is dropped)
- Accessibility-first UI (large controls, ARIA, keyboard, live region status)
- Transcript + debug panel for development
- Local-only API key via `VITE_GEMINI_API_KEY`

### Out of scope (explicitly)
Custom backend, database, RAG, knowledge base, auth, admin dashboard, location features, Kotlin Multiplatform, native apps, production-grade key handling.

## 2. Stack

| Concern | Choice |

## 3. Architecture

```
┌────────────────────────────────────────────────────┐
│ Browser (React + Vite PWA)                         │
│                                                    │
│  ┌──────────┐   ┌──────────────┐   ┌────────────┐  │
│  │ VoiceChat│──▶│useVoiceSess. │──▶│GeminiLive  │  │
│  │  + UI    │   │ (orchestrator│   │Client      │  │
│  └──────────┘   │  state mach.)│   │(@google/   │  │
│        ▲        └──┬────────┬──┘   │ genai)     │  │
│        │           │        │      └─────┬──────┘  │
│        │           ▼        ▼            │         │
│        │    ┌──────────┐ ┌──────────┐    │         │
│        └────│  Audio   │ │   Mic    │    │         │
│             │  Player  │ │ Recorder │    │         │
│             │ (24kHz)  │ │(16kHz    │    │         │
│             │ queue    │ │ worklet) │    │         │
│             └────▲─────┘ └────┬─────┘    │         │
│                  │            │PCM16     │         │
│                  │            ▼          │         │
│                  │     ┌──────────────┐  │         │
│                  └─────│ live-client  │◀─┘         │
│                        │ events       │            │
│                        └──────────────┘            │
└────────────────────────┬───────────────────────────┘
                         │ WebSocket (managed by SDK)
                         ▼
                  Gemini Live API
```

Data flow per direction:

- **Up:** mic → worklet (Float32@deviceRate) → downsample to 16 kHz Float32 → Int16 PCM → base64 → `session.sendRealtimeInput({ audio })`.
- **Down:** `onmessage` → `serverContent.modelTurn.parts[*].inlineData` (base64 PCM16@24kHz) → decode to Int16 → Float32 → `AudioBuffer` → enqueue in player.
- **Interrupt:** `serverContent.interrupted === true` → player.flush() (drops queued chunks, stops current source).

## 6. Gemini Live client

`src/lib/gemini/live-client.ts` wraps the SDK with a small event-emitter style API.

```ts
type Events = {
  onOpen?: () => void;
  onClose?: (reason?: string) => void;
  onError?: (e: Error) => void;
  onAudioChunk?: (pcm16: ArrayBuffer) => void;   // 24kHz mono
  onUserTranscript?: (text: string, isFinal: boolean) => void;
  onAssistantTranscript?: (text: string, isFinal: boolean) => void;
  onInterrupted?: () => void;
  onTurnComplete?: () => void;
  onDebug?: (event: string, data?: unknown) => void;
};

class GeminiLiveClient {
  constructor(opts: { apiKey: string; model: string; events: Events });
  connect(): Promise<void>;
  sendAudioChunk(pcm16: ArrayBuffer): void;       // base64-encodes & sends
  close(): void;
}
```

Connect uses:
```ts
ai.live.connect({
  model,
  callbacks: { onopen, onmessage, onerror, onclose },
  config: {
    responseModalities: [Modality.AUDIO],
    systemInstruction: SYSTEM_PROMPT,
    inputAudioTranscription: {},
    outputAudioTranscription: {},
  },
});
```

`sendAudioChunk` calls:
```ts
session.sendRealtimeInput({
  audio: { data: base64, mimeType: 'audio/pcm;rate=16000' },
});
```

`onmessage` parses:
- `serverContent.modelTurn.parts[*].inlineData` → audio bytes
- `serverContent.inputTranscription.text` → user transcript
- `serverContent.outputTranscription.text` → assistant transcript
- `serverContent.interrupted === true` → onInterrupted
- `serverContent.turnComplete === true` → onTurnComplete

The SDK already handles the WebSocket framing, ping/pong, and reconnection-failure surfacing — we don't reimplement WS protocol.

## 8. Audio modules

### 8.1 `pcm16.ts`
Pure functions, no side effects:
- `floatTo16BitPCM(input: Float32Array): Int16Array` — clamps to [-1, 1], scales.
- `int16ToFloat32(input: Int16Array): Float32Array`.
- `base64Encode(bytes: ArrayBuffer): string`, `base64Decode(s: string): ArrayBuffer`.
- `downsampleFloat32(input: Float32Array, fromRate: number, toRate: number): Float32Array` — naive index-based decimation. Sufficient for 48k→16k ratio (3:1) and avoids pulling in a DSP library for the POC.

### 8.2 `mic-worklet.ts`
The `AudioWorkletProcessor` source. Runs on the audio thread. For each `process()` callback it:
1. Reads mono input frame (Float32, 128 samples typically).
2. Posts the Float32Array (transferred) to main thread via `port.postMessage`.

No downsampling or PCM conversion in the worklet — keeps it tiny and lets the main thread batch.

This file is referenced via `new URL('./mic-worklet.ts', import.meta.url)` and Vite bundles it as a worklet module.

### 8.3 `mic-recorder.ts`
Main-thread wrapper.

```ts
class MicRecorder {
  start(onChunk: (pcm16: ArrayBuffer) => void): Promise<void>;
  stop(): Promise<void>;
  setMuted(muted: boolean): void;
  isActive(): boolean;
}
```

Lifecycle:
1. `getUserMedia({ audio: { echoCancellation, noiseSuppression, autoGainControl } })`.
2. Create `AudioContext` (lets browser pick rate, e.g. 48 kHz).
3. `audioContext.audioWorklet.addModule(workletUrl)`.
4. Connect `MediaStreamSource → AudioWorkletNode`.
5. On each `port.message`, batch ~80–120 ms of samples, downsample to 16 kHz, convert to PCM16, hand `ArrayBuffer` to `onChunk`. Smaller batch = lower latency, larger batch = fewer messages; we target ~100 ms (~1600 samples @16k).
6. When muted, the recorder still receives audio but does not call `onChunk` (cheap and lets us un-mute instantly).
7. `stop()` disconnects the node, stops tracks, closes context.

### 8.4 `audio-player.ts`
Queue-based PCM16 player at 24 kHz.

```ts
class AudioPlayer {
  enqueue(pcm16: ArrayBuffer): void;
  flush(): void;            // called on interruption + turn restart
  stop(): Promise<void>;
  isPlaying(): boolean;
}
```

Approach: maintain a single `AudioContext` (sampleRate forced to 24000 if supported, else convert). For each enqueued chunk, build an `AudioBuffer`, schedule via `AudioBufferSourceNode` at `nextStartTime = max(currentTime, lastEnd)`. Track ended sources. `flush()` stops outstanding scheduled sources and resets `nextStartTime`. This avoids gaps and gives us instant cancellation.

### 8.5 Why AudioWorklet over MediaRecorder/ScriptProcessor
- `MediaRecorder` produces opus/webm — not raw PCM, requires server-side decode.
- `ScriptProcessorNode` is deprecated and can glitch under main-thread load.
- `AudioWorklet` runs on the audio thread, gives us raw Float32 frames, and is the modern path.

## 9. State machine (`useVoiceSession`)

States: `idle`, `requesting-mic`, `connecting`, `listening`, `speaking`, `error`, `closed`.

Transitions:

| From | Event | To |
|---|---|---|
| idle | `start()` | requesting-mic |
| requesting-mic | mic granted | connecting |
| requesting-mic | mic denied | error |
| connecting | client.onOpen | listening |
| connecting | client.onError | error |
| listening | first audio chunk in | speaking |
| speaking | onTurnComplete + queue empty | listening |
| speaking | onInterrupted | listening (player.flush) |
| any | `stop()` | closed |
| any | client.onClose | closed |
| any | client.onError | error |

The hook exposes:
```ts
{
  status, error, micMuted,
  userTranscript, assistantTranscript,   // arrays of finalized turns + an in-progress draft
  debugEvents,                            // ring buffer (~200 entries)
  start, stop, toggleMute, reset,
}
```

## 10. Components

All voice-related components live under `src/components/voice/`.

- **VoiceChat** — top-level: lays out controls + status + transcript + debug. Reads from `useVoiceSession`.
- **VoiceControls** — Start/Stop (primary, very large), Mute, Reset. All native `<button>` with explicit `aria-label`, `aria-pressed` for toggle states, and `aria-keyshortcuts="Space"` on Start/Stop. Space and Enter both activate.
- **VoiceStatus** — `role="status"` `aria-live="polite"` region. Renders human-readable status text mapped from the state. On error it switches to `role="alert"`/`aria-live="assertive"`.
- **TranscriptPanel** — `<section aria-label="Conversation transcript">`. Renders user vs assistant turns. Hidden behind a "Show transcript" toggle for blind users (it's mainly for sighted devs); when shown, marked with a heading and uses `aria-live="off"` (we don't want SRs reading transcripts while the assistant is also speaking).
- **DebugPanel** — collapsed by default, `aria-hidden="true"` when collapsed.

## 11. Accessibility requirements

| # | Requirement | Implementation |
|---|---|---|
| A1 | Single primary action reachable in one Tab | Start/Stop is the first focusable element; auto-focused on mount |
| A2 | Keyboard-only operation | Space and Enter activate buttons; Esc stops session |
| A3 | Spoken status updates | `aria-live="polite"` region with state text; transitions debounced ≥500 ms |
| A4 | Error announcements | `role="alert"` for errors |
| A5 | High contrast | Use shadcn theme tokens; ensure focus ring visible (already in Button) |
| A6 | Large hit target | Primary button uses `size="lg"` plus an explicit min height of 80px and full-width on mobile |
| A7 | No visual-only state | Every visual badge has accompanying text |
| A8 | Reduced motion | Respect `prefers-reduced-motion` in any animations (none planned) |
| A9 | Lang attribute | `<html lang="en">` |
| A10 | Page title is descriptive | "Voice Assistant POC" |

Spoken state copy (mapped in `VoiceStatus`):
- idle → "Ready. Press space or the start button to begin."
- requesting-mic → "Requesting microphone permission."
- connecting → "Connecting."
- listening → "Listening."
- speaking → "Assistant is speaking."
- error → e.g. "Microphone permission was denied. Please grant permission and try again."
- closed → "Conversation ended."

## 12. Error handling

| Error | Surface |
|---|---|
| Missing API key at boot | UI shows blocking error; status region announces |
| `getUserMedia` rejected | `error` state with explicit "permission denied" copy |
| `AudioContext` blocked by autoplay policy | First user gesture (Start click) creates contexts — guaranteed |
| `ai.live.connect` throws | `error` state; debug log captures full error |
| Socket closes mid-session | `closed` state with "Connection ended. Press start to reconnect." |
| Worklet module fails to load | `error` state; suggests Chrome / non-private mode |

Errors are typed with a `VoiceErrorCode` union so the UI can map to friendly copy.

## 13. PWA

- `vite-plugin-pwa` with `registerType: 'autoUpdate'`.
- Manifest: name "Voice Assistant POC", start_url "/", display "standalone", theme/background colors from CSS tokens.
- Two icons (192/512 PNG) generated as plain solid-color placeholders for now.
- SW caches static assets only — Live API is realtime so explicitly bypassed.
- Installability does not unlock background mic or background networking; this is fine for Phase 1.

## 14. Testing plan

### Manual test script (matches user spec §16)

1. **Hello** — say "Hello, can you hear me?" → assistant replies by voice.
2. **Memory** — say name, ask "what's my name?" → recalls within session.
3. **Interrupt** — ask for long answer, then "Stop, make it shorter" while assistant is talking → audio cuts within ~200 ms; assistant restarts shorter.
4. **Limitation** — "Nearest bakery near me?" → assistant explains no location/db.
5. **Accessibility tone** — "How do I cross a busy road safely?" → short, clear guidance.

### Device matrix
- macOS Chrome (primary dev target)
- macOS Safari (secondary)
- Android Chrome
- iOS Safari (known: needs user gesture before any audio; we already have one)

### Automated checks (this phase)
- `pnpm typecheck` and `pnpm build` must pass.
- `pnpm lint` clean.
- No unit tests for audio modules in Phase 1 — the value is in real-device testing. Unit tests for `pcm16.ts` could be added cheaply later if instability appears.

### Latency target (informal)
- Mic → Gemini first byte: < 1500 ms after end of utterance is good for a POC.
- Interrupt → silence: < 300 ms (governed by `flush()` + scheduled-source stop).

## 16. Risks (from spec §18, with concrete mitigations)

| Risk | Mitigation here |
|---|---|
| Key in browser bundle | UI banner + README warning; `VITE_GEMINI_API_KEY` only |
| iOS Safari audio quirks | All AudioContexts created inside the user-gesture handler |
| Playback gaps | Source-node queue with absolute scheduling (`nextStartTime`) |
| Long answers | System prompt + future config for `maxOutputTokens` if needed |
| Interrupt race | `flush()` always paired with stopping currently-playing source |
| Debugging hard | Ring buffer of debug events surfaced in collapsible panel |
